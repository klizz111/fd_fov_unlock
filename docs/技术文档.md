# Fallen Doll 相机 FOV 解锁 — 技术文档

> 目标：把摄影/自由相机那条「垂直视角」滑条从 **20–90°** 解放出来，并给出可复用的
> 进程外控制层。本文记录**怎么想到的、怎么验证的、踩过什么坑**，供二次开发用。
>
> 所有结论都带实测数字。凡是"未验证"的地方会明确标注。

---

## 1. 结论摘要

| 问题 | 结论 |
|---|---|
| 引擎版本 | `UE 5.7.4-0+UE5`（`LogInit: Engine Version`），Win64 Shipping 单体包，191,914,496 字节 |
| 玩法逻辑写在哪 | **AngelScript**（`ASClass /Script/Angelscript.*`），地图与界面在 pak 内 |
| 能不能抽资产改蓝图 | 不能：pak 索引加密（`bEncryptedIndex=1`、`FPakInfo version=12`、key guid 全 0） |
| 能不能写 UE4SS Lua/C++ mod | 不能：UE4SS 在这套 exe 上**任何 FProperty 访问都崩**（见 §3） |
| 最终方案 | 进程外内存读写；指针发现两条路（UE4SS F6 manifest / 自解析 camfind） |
| 目标字段 | `UCameraComponent + 0x250` = `FieldOfView`（float），写入即时反映到渲染侧 |
| 滑块映射 | `FOV ≈ 20.4 + 69.1 × v`，`v=1.00` 即 90° 硬上限 |
| 渲染侧校验点 | `APlayerCameraManager + 0x380` = `ViewTarget.POV.FOV`，与相机字段同步 |

## 3. 为什么不用 UE4SS 的反射

UE4SS 是 UE 逆向的默认选择，但在这套 exe 上遇到了**系统性的 FProperty 崩溃**。
按时间顺序记录（都是可复现的）：

| 尝试 | 结果 |
|---|---|
| UE4SS **v4.0.0 正式版**（`#30afe5ff`） | AOB 扫描全部命中（`GUObjectArray` / `FName::ToString` / `GNatives` / `GameEngineTick`），`Using engine version: 5.7`，随后停在 `Locating KismetStringLibrary CDO...`，产出 47.8 MB dmp，**mods 根本没加载** |
| UE4SS **experimental** `v4.0.0-9-gb2d936b9` | 初始化通过，mods 正常加载，`Self test passed (6867 classes)` → 用它做注入 |
| `DumpAllObjects()`（F5） | 打出 `Dumping all objects & properties in GUObjectArray` 后 **430 ms 崩**（58.5 MB dmp），无产物 |
| `cls:ForEachProperty(...)`（Lua） | 崩 |
| `obj["FieldOfView"]`（按名读） | 崩 |
| `DumpJMAP(true/false)` | 未跑完（前置已崩） |
| `FindAllOf("Class")` / `FindAllOf("BlueprintGeneratedClass")` | **不崩**，但返回 `nil`（文档明写它只找"非 CDO 实例"，UClass 枚举走不通） |
| `FindAllOf("CameraComponent")` / `GetClass()` / `GetFullName()` / `GetAddress()` | **全部可用** |

**结论**：崩溃集中在 `FProperty` 链（`UStruct::ChildProperties` 一侧），而 UObject
指针、`FName`、`UClass`、`Outer` 都正常。于是把方案切成两半：

- **UE4SS 只负责指针**（`FindAllOf` + `GetAddress`），
- **属性读写放到进程外**（`ReadProcessMemory` / `WriteProcessMemory`）。

这就是 `mod/FDCamDump` 只做"名字 + 地址"清单、从不碰属性的原因。

顺带排除的路线：

- **改 pak / 抽蓝图**：索引加密且无 key，`checkpak.py` 里还有全量 SHA256 清单，
  动 pak 会直接破坏完整性校验。
- **Console/CVar 路线**：`GameUserSettings.ini`、`RehostSettings.ini` 里 0 个相机/FOV 键，
  FOV 夹取不是 cvar。

## 4. 偏移是怎么一步步推出来的

这一节是本文的核心：**没有符号表、没有 PDB、属性访问还会崩**，怎么把结构确定下来。

### 4.1 第一步：拿到对象指针

`mod/FDCamDump`（UE4SS Lua，v4）只做指针级操作：

```lua
local objs = FindAllOf("CameraComponent")        -- 不崩
for _, o in pairs(objs) do
    log(o:GetFullName())                          -- 完整路径，带 outer 链
    log(string.format("0x%X", o:GetAddress()))    -- 对象地址
end
```

产物 `objects.txt` 一行一个对象：

```
Class /Script/Engine.CameraComponent	<CAM_ADDR>	<CLASS_ADDR>	<OUTER_ADDR>	CameraComponent /Game/Core/Map/Room_SinglePCMain...A_FreeCameraPawn_2147477950.Camera
```

这份清单解决了两个问题：**对象地址** + **对象之间的归属关系**（第 4 列是 outer）。
注意它**只对当前进程有效**，见 §5.4。

### 4.2 第二步：锚定 FOV 字段（滑块差分法）

这是全文最有用的一招：不猜偏移，让游戏自己告诉我们。

1. 让用户把「垂直视角」滑条拖到两个不同位置；
2. 每次拍一份该对象的内存快照（`memdump.py snap`）；
3. `memdump.py diff` 只看 float 变化；
4. 唯一干净的跳变就是目标字段。

实测三轮（同一 session、同一个相机对象）：

| 滑条值 | `camera+0x250` | `PCM+0x380`（渲染侧） |
|---|---|---|
| 1.00（UI 上限） | 90.0000 | 90.0000 |
| 0.90 | 82.6573 | 82.6573 |
| 0.20 | 34.2562 | 34.2562 |

线性拟合：`FOV = 20.4273 + 69.1444 × v`，`v=1 → 89.57`，`v=0 → 20.43`。
（末端不是整数是因为采样时相机还在向目标插值；端点真实值就是 20 / 90。）

**这一步同时否掉了 `+0x254`**：早先按"FOV 后面紧跟另一个 float"的直觉写过 `+0x254`，
写 110/140 时 `PCM+0x380` 一个变化都没有——滑块差分才把它纠正过来。

> 差分法能成立的前提：**拖拽时不要让鼠标转动视角**，否则转角噪声会盖掉信号。

### 4.3 第三步：识别 PlayerCameraManager 布局

`PCM` 是判断"渲染侧到底用了多少 FOV"的唯一可信点。先猜后验：

在 PCM 内存里按十六进制找"太像默认值"的 float：

```
+0x2C8  0x42B40000  = 90.0     -> APlayerCameraManager::DefaultFOV
+0x2D0  0x44000000  = 512.0    -> DefaultOrthoWidth
+0x2D8  0x3FAAAA8F  = 1.33333  -> DefaultAspectRatio
```

三个默认值以 8 字节间隔连续出现，是一个极强的签名（`camfind` 就靠它找 PCM）。

### 4.4 第四步：从 PCM 走到"当前相机"

先验证 ViewTarget：

```
PCM + 0x340 = <PAWN_ADDR>   <-- 与 manifest 里 A_FreeCameraPawn 的地址完全一致
```

由此得到 `FViewTarget.Target` 偏移 `0x340`，而 `FMinimalViewInfo` 紧随其后：
`PCM + 0x380` 就是渲染侧正在用的 FOV（实测 87.9262，与相机 `+0x250` 的 87.93 对齐）。

再往下不需要 manifest：**在 ViewTarget 这个 Actor 的内存块里扫它的组件指针**，
条件是"指针可读 + `+0x10` 是类指针 + `+0x250` 是合理 FOV"：

```
pawn <PAWN_ADDR> + 0x2B0 -> <CAM_ADDR>   FOV=87.93  aspect=1.777778
                   ^^^^^^^^^ 命中点（不同版本/不同 Pawn 会变，所以是扫不是写死）
```

`camfind.py` 就是这条链：**扫 PCM 签名 → 读 ViewTarget → 扫该 Actor 的组件 →
用 POV FOV 交叉验证**。实测一次扫描 8017 MB 私有堆、32 秒、22 个 CameraComponent
候选、4 个 PCM 候选（只有 1 个 ViewTarget 非空）。

### 4.5 偏移总表（UE 5.7.4 Shipping）

| 偏移 | 类型 | 含义 | 校验方式 |
|---|---|---|---|
| `CameraComponent + 0x250` | float | `FieldOfView` | 拖滑条该值变；写后 `PCM+0x380` 同步 |
| `CameraComponent + 0x274` | float | `AspectRatio`（16:9 = 1.777778） | 与分辨率比例一致 |
| `PCM + 0x2C8` | float | `DefaultFOV` = 90.0 | 十六进制 `0x42B40000` |
| `PCM + 0x2D0` | float | `DefaultOrthoWidth` = 512.0 | `0x44000000` |
| `PCM + 0x2D8` | float | `DefaultAspectRatio` = 1.333333 | `0x3FAAAA8F` |
| `PCM + 0x340` | ptr | `ViewTarget.Target`（AActor*） | 等于 manifest 里 Pawn 地址 |
| `PCM + 0x380` | float | `POV.FOV`（渲染侧实际值） | 写相机后同步变化 |

## 5. 写入策略：三种模式与它们的取舍

### 5.1 pin（持续压住）

每 ~50 ms 把目标相机 `+0x250` 写成目标值。优点：简单、游戏自己的写会被立刻覆盖。
缺点：与"跟随游戏滑条"互斥（会打架）。

### 5.2 follow（跟随滑条）

读 `+0x250`，把游戏写的值（20–90）映射到目标区间（默认 60–150）再写回。

**第一版直接实时映射，结果是"拖到一半跳到 150 卡死"**。原因：游戏在拖拽时是**插值写入**
（会写出 82.6573 这种中间值），而实时映射会读回自己刚写的值继续映射 → 正反馈。

由此先验证了一个关键事实：**写进去的值，游戏不会逐帧拉回**
（写 150，10 次采样 / 3 秒全部 `HOLDS`）。说明游戏只在滑条事件时写一次。

### 5.3 settle（静默后一次性改写）—— 最终采用的方案

```
拖拽中         : 完全不介入（让游戏自己插值到它的 20–90）
静默 ≥ 350 ms  : 把最终值线性映射后写一次
写过的值       : 用 epsilon 标记为"自己写的"，不当作游戏新写入
```

`350 ms` 是经验值：大于插值间隔（帧级）又小于人手停顿的感知阈值。
`epsilon` 标记是第二版跑飞的原因——不标记的话，自己的写回被当成游戏新值再映射一次
（1.00→0.20 那轮曾出现 20 → 60 → 111.4 → 150 的级联）。

### 5.4 地址时效性（最容易踩的坑）

manifest 里的堆地址**只对当前进程有效**。重启游戏 / 换关卡后地址全变。
工具的处理：读到不合理的 FOV（不在 0.5–179）就判定"地址过期" → 提示按 F6，
或自动切换到 `camfind` 自解析。

## 6. 工程结构与数据流

```
                 ┌────────────────────────────┐
   UE4SS (可选)  │ mod/FDCamDump (Lua)        │  FindAllOf + GetAddress
                 │   → objects.txt (名字+地址) │  绝不碰 FProperty
                 └────────────┬───────────────┘
                              │ 读 manifest
┌─────────────┐   ┌───────────▼──────────────┐   ┌──────────────────────┐
│ camfind.py  │──▶│ fdcommon.py              │◀──│ fd_cam_panel.py      │
│ 自解析定位   │   │ 进程/路径/内存原语/偏移表 │   │ tkinter 面板 + 热键  │
└─────────────┘   └───────────┬──────────────┘   └──────────────────────┘
                              │
                    ┌─────────▼──────────┐
                    │ ReadProcessMemory  │ → 相机 +0x250 (写)
                    │ WriteProcessMemory │ → PCM  +0x380 (校验)
                    └────────────────────┘
```

线程模型（`fd_cam_panel.py`）：

- **主线程**：tkinter `mainloop` + 每 60 ms 的 `tick()`（刷 UI、分发热键、处理跨线程消息）
- **worker 线程**：只读写普通 Python 属性；**绝不碰 tk 变量/控件**
- **hotkey 线程**：`RegisterHotKey` + 自己的 `GetMessage` 循环，命中后塞 `queue`

## 7. 踩坑清单

每条都写了"现象 → 原因 → 修法"，都是实测踩出来的。

| # | 现象 | 原因 | 修法 |
|---|---|---|---|
| 1 | UE4SS 注入即崩，停在 `KismetStringLibrary CDO` | 正式版对 5.7 CA 布局假设有误 | 换 experimental 构建 |
| 2 | 任何属性访问崩（`DumpAllObjects`/`ForEachProperty`/`obj[x]`） | FProperty 链解析错 | **放弃 in-process 反射**，改进程外读写 |
| 3 | `FindAllOf("Class")` 返回 nil | API 只返回非 CDO 实例 | 类枚举改走 C++ dumper 或自解析 |
| 4 | 面板热键按一次跳 +4/+2，偶尔跳到 60 | 后台线程直接 `self.fov.get()` 读 tk 变量 | 线程间只传普通 Python 属性；控件操作回主线程 |
| 5 | `RegisterHotKey` 注册成功但收不到 `WM_HOTKEY` | tkinter `mainloop` 先把消息取走丢弃；且热键绑定"调用它的线程" | 独立线程注册 + 自己 `GetMessage` |
| 6 | `.bat` 双击报 `'ernal' is not recognized` | 文件是 LF 换行，cmd 逐行解析错乱 | 全部转 CRLF；且 `if (...)` 块内不放括号 |
| 7 | bat 里 `%HERE%tools\...` 找不到文件 | bat 部署在游戏根，tools 在 kit 里 | 把 `tools/` 一并部署到游戏目录 |
| 8 | `WriteProcessMemory` 报 err=87 (INVALID_PARAMETER) | PowerShell 把十六进制算成十进制再当 hex 传 | 统一 `'0x{0:X}' -f $addr` 生成地址 |
| 9 | `ReadProcessMemory` 报 err=299 (PARTIAL_COPY) | 对象跨到未提交页 | 按页读 + 失败退 64 字节粒度，返回可读部分 |
| 10 | `camfind` 扫到 0 MB，`VirtualQueryEx` 返回 0 + err=5 | `OpenProcess` 只给了 `VM_READ`；且 ctypes 未声明 `argtypes` 导致 64 位地址被按 int 截断 | 加 `PROCESS_QUERY_INFORMATION`；显式声明 `argtypes`/`restype` |
| 11 | 扫描耗时 568 秒 | Python 逐 4 字节循环 8 GB | 改 `bytes.find` 找 float 字节模式，32 秒 |
| 12 | 把 SpringArm Length 200→500，游戏崩（58.6 MB dmp） | 大跨度改值触发下游断言 | 小步长 + 写后回读校验；只改已验证字段 |
| 13 | 面板启动 Python 报 `Too early to create variable: no default root window` | 先建 `tk.StringVar` 后建 `tk.Tk` | 先建 root |

## 8. 二次开发指南

### 8.1 新增一个要改的字段

1. 用 `memdump.py dump --label X:0xADDR:0x600` 把目标对象打出来，肉眼找候选 float
   （默认值、相邻字段、十六进制特征）。
2. 用**差分法**确认：改游戏内设置 / 移动角色 → `snap` 两次 → `diff`。
3. 用 `memdump.py write` 写一个新值，**回读确认 HOLDS**，再从渲染侧/可见行为交叉验证。
4. 把偏移加进 `fdcommon.py` 的偏移表，并在 §4.5 表格里补一行（写清校验方式）。

### 8.2 游戏更新后重测偏移

按这个顺序，能最快定位断点：

```
1) camfind.py --all                # PCM 签名还灵不灵？（0x2C8/0x2D0/0x2D8）
2) 若 PCM 找到了、相机不对        # 说明 ViewTarget/组件扫描条件要调（+0x340、+0x250）
3) 若 PCM 都找不到                # DefaultFOV 默认值可能被改 → 换成 512.0/1.3333 反查
4) 找到相机后写 +0x250，看 PCM+0x380
   ├─ 同步变化   -> 偏移正确
   └─ 无变化     -> FOV 换了位置，回到 §4.2 用滑块差分重定
```

### 8.3 加一种新的交互

在 `fd_cam_panel.Panel` 里加分支即可，注意两条铁律：**worker 不碰 tk**、
**写值后回读校验**。新热键在 `Hotkeys([...])` 里加一项，`tick()` 里分发。

### 8.4 调试工具箱（`memdump.py`）

```powershell
python tools\memdump.py ps                                  # 找进程
python tools\memdump.py dump   --pid P --label Cam:0xADDR:0x800
python tools\memdump.py floats --pid P --addr 0xADDR --size 0x400 --lo 5 --hi 180
python tools\memdump.py find   --pid P --addr 0xADDR --size 0x400 --value 90 --tol 0.5
python tools\memdump.py ptrs   --pid P --addr 0xADDR --size 0x800 --ptr "Pawn=0xADDR"
python tools\memdump.py write  --pid P --addr 0xADDR --value 120   # 自动回读
python tools\memdump.py snap / diff                                 # 前后对比
python tools\memdump.py scan   --pid P --pattern 0000B442           # 全进程字节模式
```

## 9. 已知限制与路线图

**限制**

- 自解析需 30 秒且要求处于自由相机界面；非 16:9 分辨率下兜底匹配会漏。
- 只有 `FieldOfView` 一条链路做过端到端验证；其余字段（弹簧臂长度、socket offset）
  仅定位到候选，未做行为验证。
- 未验证"启动即改"（在 `LoadMap` 之前写）是否会被游戏重算覆盖。

**路线图**

1. **加速定位**：从模块基址 + 稳定偏移（`GEngine → LocalPlayer → PlayerController →
   PlayerCameraManager`）直接走，把 30 秒降到 1 秒内。需要先定位 `GEngine` 的静态指针。
2. **原生区间**：把 AngelScript 字节码里的 20/90 常量改掉，让滑条本身变成 60–150，
   不再需要常驻进程。难点：需要按区段批量读的高性能扫描器 + 字节码定位。
3. **更多字段**：把弹簧臂 `TargetArmLength` / `SocketOffset` 纳入面板，需要先做行为验证。
