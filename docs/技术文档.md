# Fallen Doll 相机 FOV 解锁 — 技术文档

> 目标：把摄影/自由相机那条「垂直视角」滑条从 **20–90°** 解放出来，并给出可复用的
> 进程外控制层。本文记录**怎么想到的、怎么验证的、踩过什么坑**，供二次开发用。
>
> 所有结论都带实测数字。凡是"未验证"的地方会明确标注。

---

## 1. 结论摘要

| 问题 | 结论 |
|---|---|
| 引擎版本 | `UE 5.7.4-0+UE5`（`LogInit: Engine Version`），Win64 Shipping 单体包，191,914,496 字节 |
| 玩法逻辑写在哪 | **AngelScript**（`ASClass /Script/Angelscript.*`），地图与界面在 pak 内 |
| 能不能抽资产改蓝图 | 不能：pak 索引加密（`bEncryptedIndex=1`、`FPakInfo version=12`、key guid 全 0） |
| 能不能写 UE4SS Lua/C++ mod | 不能：UE4SS 在这套 exe 上**任何 FProperty 访问都崩**（见 §3） |
| 最终方案 | 进程外内存读写；**定位三级降级**（§5），写入四种模式（§6） |
| 目标字段 | `UCameraComponent + 0x250` = `FieldOfView`（float），写入即时反映到渲染侧 |
| 滑块映射 | `FOV ≈ 20.4 + 69.1 × v`，`v=1.00` 即 90° 硬上限 |
| 渲染侧校验点 | `APlayerCameraManager + 0x380` = `ViewTarget.POV.FOV`，与相机字段同步 |
| 面板热键 | `Ctrl+F7/F8` ∓5°、`Ctrl+F9` 切模式、`Ctrl+F10` 显隐、`Ctrl+F11` 重扫 |
| 首次定位耗时 | manifest 路径 0 s；ViewTarget 快路径 毫秒级；全量扫描约 30 s |

**为什么能跨版本/跨副本复用**：复用的是**结构关系**，不是地址也不是名字 —— 地址每次运行都变
（缓存带 pid，换进程即作废），偏移是编译期布局且集中在 `fdcommon.py`，识别靠签名+对账而非符号名。
代价是引擎大版本改动布局时必须重测（流程见 §9.2）。

## 3. 为什么不用 UE4SS 的反射

UE4SS 是 UE 逆向的默认选择，但在这套 exe 上遇到了**系统性的 FProperty 崩溃**。
按时间顺序记录（都是可复现的）：

| 尝试 | 结果 |
|---|---|
| UE4SS **v4.0.0 正式版**（`#30afe5ff`） | AOB 扫描全部命中（`GUObjectArray` / `FName::ToString` / `GNatives` / `GameEngineTick`），`Using engine version: 5.7`，随后停在 `Locating KismetStringLibrary CDO...`，产出 47.8 MB dmp，**mods 根本没加载** |
| UE4SS **experimental** `v4.0.0-9-gb2d936b9` | 初始化通过，mods 正常加载，`Self test passed (6867 classes)` → 用它做注入 |
| `DumpAllObjects()`（F5） | 打出 `Dumping all objects & properties in GUObjectArray` 后 **430 ms 崩**（58.5 MB dmp），无产物 |
| `cls:ForEachProperty(...)`（Lua） | 崩 |
| `obj["FieldOfView"]`（按名读） | 崩 |
| `DumpJMAP(true/false)` | 未跑完（前置已崩） |
| `FindAllOf("Class")` / `FindAllOf("BlueprintGeneratedClass")` | **不崩**，但返回 `nil`（文档明写它只找"非 CDO 实例"，UClass 枚举走不通） |
| `FindAllOf("CameraComponent")` / `GetClass()` / `GetFullName()` / `GetAddress()` | **全部可用** |

**结论**：崩溃集中在 `FProperty` 链（`UStruct::ChildProperties` 一侧），而 UObject
指针、`FName`、`UClass`、`Outer` 都正常。于是把方案切成两半：

- **UE4SS 只负责指针**（`FindAllOf` + `GetAddress`），
- **属性读写放到进程外**（`ReadProcessMemory` / `WriteProcessMemory`）。

这就是 `mod/FDCamDump` 只做"名字 + 地址"清单、从不碰属性的原因。

顺带排除的路线：

- **改 pak / 抽蓝图**：索引加密且无 key，`checkpak.py` 里还有全量 SHA256 清单，
  动 pak 会直接破坏完整性校验。
- **Console/CVar 路线**：`GameUserSettings.ini`、`RehostSettings.ini` 里 0 个相机/FOV 键，
  FOV 夹取不是 cvar。

## 4. 偏移是怎么一步步推出来的

这一节是本文的核心：**没有符号表、没有 PDB、属性访问还会崩**，怎么把结构确定下来。

### 4.1 第一步：拿到对象指针（可选路径）

`mod/FDCamDump`（UE4SS Lua，v4）只做指针级操作：

```lua
local objs = FindAllOf("CameraComponent")        -- 不崩
for _, o in pairs(objs) do
    log(o:GetFullName())                          -- 完整路径，带 outer 链
    log(string.format("0x%X", o:GetAddress()))    -- 对象地址
end
```

产物 `objects.txt` 一行一个对象：

```
Class /Script/Engine.CameraComponent	<CAM_ADDR>	<CLASS_ADDR>	<OUTER_ADDR>	CameraComponent /Game/...A_FreeCameraPawn_2147477950.Camera
```

这份清单解决了两个问题：**对象地址** + **对象之间的归属关系**（第 4 列是 outer）。
它**只对当前进程有效**，且是可选路径 —— 没有它也能玩（§5 的三级降级）。

### 4.2 第二步：锚定 FOV 字段（滑块差分法）

这是全文最有用的一招：不猜偏移，让游戏自己告诉我们。

1. 让用户把「垂直视角」滑条拖到两个不同位置；
2. 每次拍一份该对象的内存快照（`memdump.py snap`）；
3. `memdump.py diff` 只看 float 变化；
4. 唯一干净的跳变就是目标字段。

实测三轮（同一 session、同一个相机对象）：

| 滑条值 | `camera+0x250` | `PCM+0x380`（渲染侧） |
|---|---|---|
| 1.00（UI 上限） | 90.0000 | 90.0000 |
| 0.90 | 82.6573 | 82.6573 |
| 0.20 | 34.2562 | 34.2562 |

线性拟合：`FOV = 20.4273 + 69.1444 × v`，`v=1 → 89.57`，`v=0 → 20.43`。
（末端不是整数是因为采样时相机还在向目标插值；端点真实值就是 20 / 90。）

**这一步同时否掉了 `+0x254`**：早先按"FOV 后面紧跟另一个 float"的直觉写过 `+0x254`，
写 110/140 时 `PCM+0x380` 一个变化都没有——滑块差分才把它纠正过来。

> 差分法能成立的前提：**拖拽时不要让鼠标转动视角**，否则转角噪声会盖掉信号。

### 4.3 第三步：识别 PlayerCameraManager 布局

`PCM` 是判断"渲染侧到底用了多少 FOV"的唯一可信点。先猜后验：

在 PCM 内存里按十六进制找"太像默认值"的 float：

```
+0x2C8  0x42B40000  = 90.0     -> APlayerCameraManager::DefaultFOV
+0x2D0  0x44000000  = 512.0    -> DefaultOrthoWidth
+0x2D8  0x3FAAAA8F  = 1.33333  -> DefaultAspectRatio
```

三个默认值以 8 字节间隔连续出现，是一个极强的签名（`camfind` 就靠它找 PCM）。

### 4.4 第四步：从 PCM 走到"当前相机"

先验证 ViewTarget：

```
PCM + 0x340 = <PAWN_ADDR>   <-- 与 manifest 里 A_FreeCameraPawn 的地址完全一致
```

由此得到 `FViewTarget.Target` 偏移 `0x340`，而 `FMinimalViewInfo` 紧随其后：
`PCM + 0x380` 就是渲染侧正在用的 FOV（实测 87.9262，与相机 `+0x250` 的 87.93 对齐）。

再往下**不需要 manifest**：在 ViewTarget 这个 Actor 的内存块（0x6000 字节）里扫它的
组件指针，条件是"指针落在私有可写页 + `+0x10` 是类指针 + `+0x250` 是合理 FOV"：

```
pawn <PAWN_ADDR> + 0x2B0 -> <CAM_ADDR>   FOV=87.93  aspect=1.777778
                   ^^^^^^^^^ 命中点（不同版本/不同 Pawn 会变，所以是扫不是写死）
```

`camfind.cameras_from_viewtarget()` 就是这条链（毫秒级，不扫堆）；`camfind.pick_active()`
再用 `PCM+0x380` 的 POV FOV 与候选做对账（误差 < 0.05）确认"谁在出画面"。

### 4.5 偏移总表（UE 5.7.4 Shipping）

| 偏移 | 类型 | 含义 | 校验方式 |
|---|---|---|---|
| `CameraComponent + 0x250` | float | `FieldOfView` | 拖滑条该值变；写后 `PCM+0x380` 同步 |
| `CameraComponent + 0x274` | float | `AspectRatio`（16:9 = 1.777778） | 与分辨率比例一致 |
| `PCM + 0x2C8` | float | `DefaultFOV` = 90.0 | 十六进制 `0x42B40000` |
| `PCM + 0x2D0` | float | `DefaultOrthoWidth` = 512.0 | `0x44000000` |
| `PCM + 0x2D8` | float | `DefaultAspectRatio` = 1.333333 | `0x3FAAAA8F` |
| `PCM + 0x340` | ptr | `ViewTarget.Target`（AActor*） | 等于 manifest 里 Pawn 地址 |
| `PCM + 0x380` | float | `POV.FOV`（渲染侧实际值） | 写相机后同步变化 |

权威定义在 `fdcommon.py` 的 `OFF_*` 常量（L39-45）。

### 4.6 偏移的单一来源（已收敛）

曾经 `tools/camfind.py` 里裸写了 3 处偏移（`+0x380` ×2、`VT_OFF = 0x340`），
版本更新时会把"改一处"退化成"改三处"。**现已全部收敛**：

- 偏移只在 `fdcommon.py` 定义（`OFF_*`，L39-47），其他文件一律引用 `fd.OFF_*`；
- `camfind.py` 保留 `VT_OFF` / `FOV_OFF` / `AR_OFF` / `PCM_FOV_OFF` 作为**别名**
  （面板侧用 `camfind.VT_OFF`），但值全部来自 `fd`；
- 读取长度改用 `HEAD_LEN = fd.OFF_ASPECT + 4`，不再出现 `0x2A0` / `0x280` 这类魔数；
- `tests/test_offsets.py` 用 **ast 级静态扫描**守住这条约定：任何 `tools/*.py` 里
  出现 `0x250/0x274/0x2C8/0x2D0/0x2D8/0x340/0x380` 字面量都会失败
  （注释和 docstring 里写这些数字不会误报）。

> 换句话说：以后换版本只需要改 `fdcommon.py` 一处 + 跑 `tests/test_offsets.py`，
> 不用再去别的文件里找残留。

## 5. 定位策略：三级降级

面板不是"一种找法"，而是三级依次降级，越往后越慢、越不依赖前置条件。

```
① manifest（objects.txt）        0 s        需要装 UE4SS，且按 Ctrl… 按一次 F6
        ↓ 没有 / 地址过期
② ViewTarget 快路径              毫秒级      只要 PCM 还在缓存里，且游戏在画面里
        ↓ 没有缓存的 PCM / 快路径失败
③ 全量扫描（私有堆）              ~30 s      扫签名找 PCM，再走 ② 的链
```

### 5.1 manifest 路径（最快，但要 UE4SS）

`parse_objects()` 读 `objects.txt`，按 `--filter`（默认 `A_FreeCameraPawn`）筛出相机。
缺点：**名字过滤会漏**（第一人称相机在 `AvatarPawn` 上，不含 `A_FreeCameraPawn`），
且地址随进程失效。

### 5.2 ViewTarget 快路径（默认主力）

`camfind.cameras_from_viewtarget(h, pcms, size=0x6000)`：

1. 读 `PCM + 0x340` 得到 ViewTarget Actor；
2. 在它的 0x6000 字节内按 8 字节步进取指针；
3. 三道校验：`plausible_ptr` → `is_private()`（`MEM_COMMIT` + `MEM_PRIVATE` + 可写，
   排除 exe/dll 映像段）→ `FOV ∈ [5,179] 且 AspectRatio ∈ [0.5,3.0]`；
4. 命中即返回，**不扫堆**。

面板优先取 `outer == ViewTarget` 的那一个（`viewtarget-owner`，最可信），否则用
`pick_active()` 按 POV FOV 对账挑最接近的。

### 5.3 全量扫描（兜底，~30 s）

`camfind.scan(h, lo=None, hi=None, throttle_ms=0, workers=8, stop_on_pcm=False)`：

- 只枚举 `MEM_PRIVATE` 可写页，按 32 MB 分块（overlap 0x400）；
- `ThreadPoolExecutor(workers=8)` 并行读 —— ctypes 调用会释放 GIL，实测比单线程快一个量级；
- 用 `bytes.find` 找 float 字节模式（`16/9` 的 `39 8E E3 3F`、`90.0` 的 `00 00 B4 42`），
  不是逐 4 字节 Python 循环（那样要 568 秒）；
- `stop_on_pcm=True`：一旦找到带合法 ViewTarget 的 PCM 就立刻收工，转 ②；
- `lo/hi`：面板会先用 `last_cam ± 0x10000000` 做窄扫，失败才全量；
- `throttle_ms`：面板用 2~3 ms 限速，避免把游戏卡死。

实测：8017 MB 私有堆、约 32 秒、22 个相机候选、4 个 PCM 候选（只有 1 个 ViewTarget 非空）。

### 5.4 失效与自愈

| 失效场景 | 检测方式 | 自愈动作 |
|---|---|---|
| 游戏重启 | `find_pid()` 每 2 s 比对 pid | 清 `pin_targets`/`pcms`/`all_cams`，自动重扫 |
| 单个相机对象释放 | 每次写前读 `+0x250`，值不在 `[0.5,179]` | 从 `pin_targets`/`cams` 剔除并落盘 |
| 切了视角（相机换了） | 每拍读 `PCM+0x380`，与目标差 >1.0° | 连续 2 拍不达标且距上次 >3 s → `fast_relocate()`，失败再全量 |
| 在标题/菜单里 | 所有 PCM 的 ViewTarget 都是 0 | 提示"进游戏画面后再扫"，**不启动 9 GB 扫描** |

## 6. 写入策略：四种模式与它们的取舍

### 6.1 pin（持续压住，默认）

每 ~50 ms 把 `self.cams` 里**所有**目标相机写成目标值。简单、能压住游戏自己的写。

### 6.2 follow（跟随滑条）

读 `+0x250`，把游戏写的值（20–90）映射到目标区间（默认 60–150）再写回。

**第一版直接实时映射，结果是"拖到一半跳到 150 卡死"**。原因：游戏在拖拽时是**插值写入**
（会写出 82.6573 这种中间值），实时映射会读回自己刚写的值继续映射 → 正反馈。

### 6.3 settle（静默后一次性改写）—— follow 的最终实现

```
拖拽中         : 完全不介入（让游戏自己插值到它的 20–90）
静默 ≥ 350 ms  : 把最终值线性映射后写一次
写过的值       : 用 epsilon 标记为"自己写的"，不当作游戏新写入
```

`350 ms` 是经验值：大于插值间隔（帧级）又小于人手停顿的感知阈值。
`epsilon` 标记是第二版跑飞的原因——不标记的话，自己的写回被当成游戏新值再映射一次
（1.00→0.20 那轮曾出现 20 → 60 → 111.4 → 150 的级联）。

前提事实：**写进去的值游戏不会逐帧拉回**（写 150，10 次采样 / 3 秒全部 `HOLDS`），
所以写完就稳定，不需要持续对抗。

### 6.4 multi-pin（多目标累积）—— 覆盖第一人称的关键

`pin_targets` 是个**只增不减的集合**（除进程变化），`self.cams` 每次从它重建，
`apply()` 遍历整个列表写。所以：

```
在自由相机里定位 → pin_targets = {自由相机}
切到第一人称   → POV 不达标 → 重定位 → pin_targets = {自由相机, FPV 相机}
              → 两个相机同时被压值
```

这解释了"为什么第一人称也能改"：不是识别变了，是**写入集合变成了多目标**，
加上 §5.2 的 ViewTarget 链本来就不看名字。

> 注意：`self.broadcast`（源码注释写"扫描到的所有玩家相机 FOV>=60，全部一起压值"）
> 是**未完成的死代码** —— 只有声明与清理，全仓没有任何一处往里 append。
> 真正起作用的是 `pin_targets` + POV 闭环，别照着那行注释调参。

### 6.5 apply() 的守门规则

每次写前复核（`tools/fd_cam_panel.py` L402-417）：

- 对象仍可读；
- `FOV ∈ [5, 179]`；
- `AspectRatio ∈ [1.60, 2.00]`；
- 值已等于目标则不写（省掉无谓写）。

**这条 AR 白名单比 `cameras_from_viewtarget` 的 `[0.5, 3.0]` 更严**：21:9（2.33）或
强制 4:3（1.33）的相机会被识别、也会被认定为 active，但 `apply()` 会**静默跳过**，
表现是"定位成功但画面没变"。遇到就把它放宽到 `[0.5, 3.0]` 对齐。

## 7. 工程结构与数据流

```
                 ┌────────────────────────────┐
   UE4SS (可选)  │ mod/FDCamDump (Lua)        │  FindAllOf + GetAddress
                 │   → objects.txt (名字+地址) │  绝不碰 FProperty
                 └────────────┬───────────────┘
                              │ ① manifest
┌─────────────┐   ┌───────────▼──────────────┐   ┌──────────────────────┐
│ camfind.py  │──▶│ fdcommon.py              │◀──│ fd_cam_panel.py      │
│ ② 快路径     │   │ 进程/路径/内存原语/偏移表 │   │ tkinter 面板 + 热键  │
│ ③ 全量扫描   │   │  find_pid (纯 ctypes)    │   │ pin_targets 缓存     │
└─────────────┘   └───────────┬──────────────┘   └──────────────────────┘
                              │
                    ┌─────────▼──────────┐
                    │ ReadProcessMemory  │ → 相机 +0x250 (写)
                    │ WriteProcessMemory │ → PCM  +0x380 (校验/闭环)
                    └────────────────────┘
```

**线程模型**（`fd_cam_panel.py`）：

- **主线程**：tkinter `mainloop` + 每 60 ms 的 `tick()`（刷 UI、分发热键、处理跨线程消息）
- **worker 线程**：pin/follow 写入、pid 看护、POV 闭环；**绝不碰 tk 变量/控件**
- **locate 线程**：`auto_locate()` 起的扫描线程，结束后把结果交给主线程
- **hotkey 线程**：`RegisterHotKey` + 自己的 `GetMessage` 循环，命中后塞 `queue`

**落在盘上的状态**：`tools/pin_targets.json` = `{"pid": ..., "addrs": [...], "pcms": [...]}`。
同一 pid 内下次启动直接复用（状态栏"已恢复 N 个相机"），pid 一变自动作废（已加进 `.gitignore`）。

## 8. 踩坑清单

每条都写了"现象 → 原因 → 修法"，都是实测踩出来的。

| # | 现象 | 原因 | 修法 |
|---|---|---|---|
| 1 | UE4SS 注入即崩，停在 `KismetStringLibrary CDO` | 正式版对 5.7 布局假设有误 | 换 experimental 构建 |
| 2 | 任何属性访问崩（`DumpAllObjects`/`ForEachProperty`/`obj[x]`） | FProperty 链解析错 | **放弃 in-process 反射**，改进程外读写 |
| 3 | `FindAllOf("Class")` 返回 nil | API 只返回非 CDO 实例 | 类枚举改走 C++ dumper 或自解析 |
| 4 | 面板热键按一次跳 +4/+2，偶尔跳到 60 | 后台线程直接读 tk 变量 | 线程间只传普通 Python 属性；控件操作回主线程 |
| 5 | `RegisterHotKey` 注册成功但收不到 `WM_HOTKEY` | tkinter `mainloop` 先把消息取走丢弃；且热键绑定"调用它的线程" | 独立线程注册 + 自己 `GetMessage` |
| 6 | `.bat` 双击报 `'ernal' is not recognized` | 文件是 LF 换行，cmd 逐行解析错乱 | 全部转 CRLF；`if (...)` 块内不放括号 |
| 7 | bat 里 `%HERE%tools\...` 找不到文件 | bat 部署在游戏根，tools 在 kit 里 | 把 `tools/` 一并部署到游戏目录 |
| 8 | `WriteProcessMemory` 报 err=87 (INVALID_PARAMETER) | PowerShell 把十六进制算成十进制再当 hex 传 | 统一 `'0x{0:X}' -f $addr` 生成地址 |
| 9 | `ReadProcessMemory` 报 err=299 (PARTIAL_COPY) | 对象跨到未提交页 | 按页读 + 失败退 64 字节粒度，返回可读部分 |
| 10 | `camfind` 扫到 0 MB，`VirtualQueryEx` 返回 0 + err=5 | `OpenProcess` 只给了 `VM_READ`；且 ctypes 未声明 `argtypes` 导致 64 位地址被按 int 截断 | 加 `PROCESS_QUERY_INFORMATION`；显式声明 `argtypes`/`restype` |
| 11 | 扫描耗时 568 秒 | Python 逐 4 字节循环 8 GB | 改 `bytes.find` + 8 线程并行，32 秒 |
| 12 | 把 SpringArm Length 200→500，游戏崩（58.6 MB dmp） | 大跨度改值触发下游断言 | 小步长 + 写后回读校验；只改已验证字段 |
| 13 | 面板启动报 `Too early to create variable: no default root window` | 先建 `tk.StringVar` 后建 `tk.Tk` | 先建 root |
| 14 | 调用 `find_pid()` 时闪一下黑窗 | 走 `subprocess` 调 `tasklist` | 改纯 ctypes `CreateToolhelp32Snapshot`，且进程名**精确匹配**（`python.exe` 不会误中 `pythonw.exe`） |
| 15 | 候选里混进大量假相机 | 只校验 FOV/AR，指针可能落在模块映像段 | 加 `is_private()`：必须 `MEM_PRIVATE` + 可写页 |
| 16 | 定位成功但画面不变（非 16:9） | `apply()` 的 AR 白名单 `[1.60,2.00]` 比扫描侧 `[0.5,3.0]` 更严 | 放宽 `apply()` 的 AR 区间 |
| 17 | 切视角后不生效 | 只 pin 单个 active 相机 | `pin_targets` 累积 + POV 闭环自动重定位（§6.4） |
| 18 | 想在菜单里扫描，结果卡 30 秒 | ViewTarget 全 0 仍在扫堆 | 先判所有 PCM 的 ViewTarget，全 0 就提示并跳过 |

## 9. 二次开发指南

### 9.1 新增一个要改的字段

1. 用 `memdump.py dump --label X:<ADDR>:0x600` 把目标对象打出来，肉眼找候选 float
   （默认值、相邻字段、十六进制特征）；
2. 用**差分法**确认：改游戏内设置 / 移动角色 → `snap` 两次 → `diff`；
3. 用 `memdump.py write` 写一个新值，**回读确认 HOLDS**，再从渲染侧/可见行为交叉验证；
4. 把偏移加进 `fdcommon.py` 的偏移表，并在 §4.5 表格里补一行（写清校验方式）。

### 9.2 游戏更新后重测偏移

```
1) camfind.py --all                # PCM 签名还灵不灵？（0x2C8/0x2D0/0x2D8）
2) 若 PCM 找到了、相机不对        # ViewTarget/组件扫描条件要调（0x340、0x250）
3) 若 PCM 都找不到                # DefaultFOV 默认值可能被改 → 换成 512.0/1.3333 反查
4) 找到相机后写 +0x250，看 PCM+0x380
   ├─ 同步变化   -> 偏移正确
   └─ 无变化     -> FOV 换了位置，回到 §4.2 用滑块差分重定
5) 全绿后跑 fd_cam_panel.py --selftest（写 60/150/110 各一次并回读）
   python tests\test_offsets.py     # 偏移值与「tools/*.py 不得有偏移字面量」约定
   python tests\test_paths.py       # 路径解析（game-dir / 环境变量 / exe 反查）
```

### 9.3 加一种新的交互

在 `fd_cam_panel.Panel` 里加分支即可，铁律：**worker 不碰 tk**、**写值后回读校验**。
新热键在 `Hotkeys([...])` 里加一项（`Ctrl+F7..F11` 已占用），`tick()` 里分发。

### 9.4 定位链断了怎么排查

按三级降级顺序倒着查，最快定位断点：

```
Ctrl+F11（强制重扫）
 ├─ 状态栏"当前没有活动的视图目标"   -> 不在游戏画面里，属正常保护
 ├─ 状态栏"自动定位失败"            -> 走到 pick_active 仍无候选：查 AR 白名单 / 扫描范围
 └─ 状态栏"定位成功" 但画面不变     -> apply() 被 AR 白名单挡了，或写后游戏覆盖
```

### 9.5 多副本 / 多版本共存

- 路径解析链：`--game-dir` → `FDMOD_GAME_DIR` → `config.json` → **从运行进程反查**
- 每个安装副本是独立进程、独立 pid，`pin_targets.json` 各写各的，互不串
- 同一份 `tools/` 可以被多个副本共用，只要 `fdcommon.py` 在 `tools/` 的上一级

### 9.6 调试工具箱（`memdump.py`）

```powershell
python tools\memdump.py ps                                  # 找进程
python tools\memdump.py dump   --pid P --label Cam:0xADDR:0x800
python tools\memdump.py floats --pid P --addr 0xADDR --size 0x400 --lo 5 --hi 180
python tools\memdump.py find   --pid P --addr 0xADDR --size 0x400 --value 90 --tol 0.5
python tools\memdump.py ptrs   --pid P --addr 0xADDR --size 0x800 --ptr "Pawn=0xADDR"
python tools\memdump.py write  --pid P --addr 0xADDR --value 120   # 自动回读
python tools\memdump.py snap / diff                                 # 前后对比
python tools\memdump.py scan   --pid P --pattern 0000B442           # 全进程字节模式
```

## 10. 已知限制与路线图

**限制**

- 首次定位仍需全量扫描（约 30 s，游戏会卡顿）；之后走 ViewTarget 快路径是毫秒级。
- 自解析要求处于游戏画面内（标题/菜单里 ViewTarget 为 0，工具会拒绝扫堆）。
- `apply()` 的 AR 白名单 `[1.60,2.00]` 会让非 16:9 分辨率静默失效（§6.5）。
- 只有 `FieldOfView` 一条链路做过端到端验证；弹簧臂长度、socket offset 仅定位到候选。
- `self.broadcast` 是死代码（§6.4 注），不要照注释调参。
- `camfind.py` 仍有 3 处裸写偏移（§4.6）。

**路线图**

1. ~~**统一偏移**~~：已完成（§4.6），并由 `tests/test_offsets.py` 静态守护。
2. **秒级冷启动**：从模块基址 + 稳定偏移（`GEngine → LocalPlayer → PlayerController →
   PlayerCameraManager`）直接走，免掉首次 30 s 扫描。需要先定位 `GEngine` 静态指针。
3. **原生区间**：改 AngelScript 字节码里的 20/90 常量，让滑条本身变成 60–150，
   不再需要常驻进程。需要高性能区段扫描器 + 字节码定位。
4. **更多字段**：把弹簧臂 `TargetArmLength` / `SocketOffset` 纳入面板（先做行为验证）。
